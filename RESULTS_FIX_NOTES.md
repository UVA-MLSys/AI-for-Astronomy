# AWS results pipeline fix notes

Goal: `aws/stats.py` with default options regenerates the published paper results again. The paper results are 28 configurations (25/50/75/100 MB partitions x 1, 2, 4, 6, 8, 10, 12.6 GB) plus the batch size sweep, as of commit 566e722 ("update results with paper"). The later large-scale (100 GB to 1 TB) and S3 timing runs are kept, but they now live in `aws/results/large_scale/` and are opt-in.

Nothing was staged or committed. `aws/lambda/`, `aws/statemachine/` and `.idea/` were not touched. No AWS calls were made.

## What was wrong at HEAD

- `stats.py` hardcoded the large sizes and `timing` into its default size list, so every run mixed them into the paper tables.
- 0e4821e overwrote `aws/result-partition-100MB/total/{1,2,3}/combined_data.json` (the paper 12.6 GB / 100 MB runs) with the S3 timing rerun. The `result_path` inside is `.../12GB/timing/{run}`, and run 2 has only 8 of 130 workers. It also deleted `total100GB/timing/*`, which held byte-identical copies of the same three files. So the 100 MB / 12.6 GB rows in `result_stats.csv` came from the timing rerun.
- `state_machine_logs.csv` was regenerated with only large and timing rows. The 28 paper configurations and the batch sweep were gone. The notebook cell that converts labels to numbers had failed on `'timing'` (the error is saved in the HEAD notebook), so the file was written without `num_worlds` and with string labels.
- As a result, `result_stats_adjusted.csv` held only large rows plus one 50 MB / 2 GB row from an unrelated rerun (58.63 s). `batch_varying_adjusted.csv` was header only. `plots.ipynb` reads both, so it could no longer reproduce the paper figures.
- `aws/figures/cai_inference_time.jpg` and `cai_throughput.jpg` (README Fig 2 and Fig 3) were overwritten in cfb522b with a near-empty plot of two points (50 MB at 2 GB and 100 MB at 100 GB). They are produced by `code/Anomaly Detection/Plots/CosmicAIPlots.ipynb`, which reads the same CSV. The 566e722 versions are the paper figures.
- `plots.ipynb` itself changed after 566e722 only by IDE reformatting (cell key order and execution metadata). No code changed, so it was left alone.

- `aws/results/large_scale/state_machine_logs.csv`: the HEAD `aws/results/state_machine_logs.csv`, copied unchanged

Edited:
- `aws/stats.py`
  - argparse options `--data-sizes`, `--partitions`, `--runs`, `--batch-sizes`, `--results-dir`. The defaults are the paper's 7 sizes, 4 partitions, 3 runs, 5 batch sizes and `./results`.
  - `--batch-sizes` with no values skips the batch sweep.
  - All input and output paths go through `--results-dir`.
  - The elif chain became a `DATA_SIZE_GB` table plus `data_size_in_gb()`.
  - It exits with an error if two size labels map to the same GB value (for example `total` and `timing`). Before, they would silently merge into one group.
  - S3 metric handling from 0e4821e is unchanged.
- `aws/collect_logs.ipynb`
  - New config cell after the imports: `data_sizes` (label to GB, paper default) and `output_path` (default `./results/state_machine_logs.csv`).
  - The filter cell keeps only configured labels.
  - The conversion cell maps labels through `data_sizes`, so `timing` and `1TB` no longer crash it. Its stale error output was cleared.
  - The save cell writes to `output_path`.
  - Otherwise unchanged. It still validates as nbformat 4.2.

## Verification

All checks were run from `aws/` in the `cylon_dev` env.

1. `python stats.py` (defaults): `result_stats.csv`, `result_stats_adjusted.csv`, `batch_varying_results.csv` and `batch_varying_adjusted.csv` are **byte-identical** to 566e722. There are no differences, not even in the rounding.
2. `python stats.py --data-sizes total100GB total256GB total512GB total768GB total1000GB timing --partitions 100 --batch-sizes --results-dir ./results/large_scale`:
   - `result_stats.csv` (24 rows) is text-identical to the HEAD rows for 100 MB at 12.6 GB and above.
   - `result_stats_adjusted.csv` (16 rows) is text-identical to the HEAD file minus the 50 MB / 2 GB rerun rows. That row's state log entry is still kept in `large_scale/state_machine_logs.csv`.
   - No large-scale `batch_varying_*` files are written. At HEAD, `batch_varying_adjusted.csv` was empty because no large run is a batch run.
3. `python stats.py --data-sizes total timing` fails with the duplicate-size error, as intended.
4. Notebook cells 5 to 8 were run offline with a synthetic `results` dict (no boto3 calls), using both the paper config and a large config. They produce correct CSVs: the paper config gives `num_worlds` 41 for 25 MB / 1 GB and 130 for 100 MB / 12.6 GB, and the large config maps `1TB` to 1000 and `timing` to 12.6. Cells that call AWS were not run.
5. `plots.ipynb` ran headless with `jupyter nbconvert --execute` on a scratch copy, with no errors. The four regenerated figures (`inference_time`, `throughput`, `batch_varying_inference_time`, `batch_varying_throughput`) show the same data as the committed 566e722 figures. They differ only by about 20 px in image size, from matplotlib and font versions. The repo figures were not overwritten.
6. `CosmicAIPlots.ipynb` (the source of `cai_*.jpg`) was not run. It needs seaborn, which is not in the env, and it lives outside `aws/`. The two `cai_*.jpg` files were restored from 566e722 instead.

## Open points for the large-scale data (not changed, documented in the large_scale README)

- For 256 GB and above, every `combined_data.json` holds exactly 1000 entries. The summarizer called `list_objects_v2` without pagination. So CPU time, memory, throughput and `total_bits` cover only 1000 workers. The Step Functions durations are usable.
- The `total100GB` data says `983GB` in `result_path` and has 983 entries. The state log has both `100GB` and `983GB` rows with different durations, and the adjusted table joins on the `100GB` ones. These may come from different runs.
- `1TB` and `timing` state log rows do not join, because their labels are not numeric. They become joinable if the logs are recollected with the new notebook config.

## Heads-up for the co-author who ran the large-scale sweep

Your 100 GB to 1 TB and S3 timing results are all still in the repo. They now live in `aws/results/large_scale/`, and the timing `combined_data.json` files moved to `aws/result-partition-100MB/timing/`, so they no longer overwrite the paper tables and figures. To regenerate them, run `stats.py` with `--data-sizes ... --results-dir ./results/large_scale` (the exact command is in `aws/results/large_scale/README.md`), and set the new config cell in `collect_logs.ipynb` before collecting logs. Please also check the README caveat: for 256 GB and up, the per-worker metrics cover only 1000 workers because of the unpaginated `list_objects_v2` call in the summarizer.
